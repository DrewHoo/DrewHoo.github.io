**Low severity — a handful of small correctness nits, batched into one issue. None urgent.**

1. **`sampleRouteStops()` never returns the actual origin as the "Start" stop.** For `s = 0`, `targetDist` is `0`, and the very first loop iteration satisfies `acc + segLengths[0] >= 0`, so `point = coords[1]` — the second route coordinate, not the first. With OSRM's dense `overview=full` geometry the error is a few meters, so this is invisible in practice, but it's an off-by-one waiting to matter if the sampling logic is ever reused. Special-casing it is the clearest fix:

   ```js
   if (targetDist === 0) { stops.push({ lat: coords[0].lat, lon: coords[0].lon, ... }); continue; }
   ```

2. **`closestHour()` clamps silently past the forecast horizon.** The hourly request fetches `forecast_days=3`. A long multi-day plan (or a late departure plus the pace corrections from the ETA issue) can push an arrival past the last available hour, and `closestHour()` will quietly return that last hour as if it were the real forecast. Cheap guard: if the best match is more than ~90 minutes from the target, mark the stop card "beyond forecast" instead of showing confident numbers.

3. **`precipPct` can render as `null% precip`.** Open-Meteo's `precipitation_probability` can be null for some hours/regions. The stop-card template interpolates it directly. One-character-class fix: `${stop.forecast.precipPct ?? "–"}% precip`.

4. **`manifest.json` reuses one icon for `"purpose": "any maskable"`.** A maskable icon needs the artwork inside the central "safe zone" because Android crops it to a circle/squircle; an icon designed for `any` typically bleeds to the edges and gets its corners eaten. Either export a padded variant as a separate `"purpose": "maskable"` entry, or drop `maskable` and let Android letterbox it.

5. **Stop cards are built with `innerHTML` string interpolation.** Every interpolated value today is a number, an emoji, or an internally generated compass string, so there's no actual injection risk — but the first time user-entered text (e.g. a stop name from the geocoder-choices feature) lands in that template it becomes one. Habit-level suggestion: build stop cards with `createElement`/`textContent`, matching how the rest of the app already does DOM updates.

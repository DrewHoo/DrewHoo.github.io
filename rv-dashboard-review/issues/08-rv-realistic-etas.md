**Enhancement — ETAs assume car speeds and zero breaks, so late-day forecasts can be matched to the wrong hour.**

`route.durationSeconds` comes straight from OSRM, which models a **passenger car** driving **nonstop**. A typical RV runs 5–15 mph under the car estimate on highways, and a travel day includes fuel, food, and leg-stretch stops. On a 6–8 hour day the real arrival can easily run 1.5–3 hours behind the OSRM estimate.

That matters here specifically because the whole feature is "forecast at the hour you'll be there": `closestHour()` picks the forecast nearest the ETA, and afternoon wind (the thing this app exists to warn about) often builds hour by hour. An ETA that's 2 hours optimistic samples the calmer early-afternoon forecast at what will actually be a late-afternoon arrival.

### Suggested fix: two small settings, simple math

Add to the settings card (persisted in `localStorage` next to the wind thresholds):

- **"My pace vs. car estimate"** — a percentage, default ~85% for a large rig or towing.
- **"Break time per 4 hours driving"** — minutes, default ~30.

Then stretch the duration once, right after the route comes back:

```js
const paceFactor = settings.pacePct / 100;                    // e.g. 0.85
let adjusted = route.durationSeconds / paceFactor;            // slower cruise
const breaks = Math.floor(adjusted / (4 * 3600)) * settings.breakMin * 60;
adjusted += breaks;
route.durationSeconds = adjusted;
```

Everything downstream — `sampleRouteStops()`'s per-stop ETAs, the "about X hr driving" status line, the forecast matching — picks up the correction automatically because it all derives from `durationSeconds`.

(Optional companion: the planner is hard-wired to "tomorrow" via `nextOccurrenceOfTime()`. A small "Today / Tomorrow" choice would reuse all the same machinery — the hourly request already fetches 3 days — and covers the "we're leaving in an hour, what's ahead?" case.)

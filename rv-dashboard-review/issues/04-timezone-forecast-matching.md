**Severity: medium — route forecasts are matched to the wrong hour whenever a route crosses a time zone. One-line fix.**

`weather.js` requests hourly forecasts with `&timezone=auto`, which makes Open-Meteo return each hour's `time` as a **local wall-clock string with no UTC offset** — e.g. `"2026-08-20T14:00"` meaning *2pm at the forecast location*. This line:

```js
time: new Date(t),
```

hands that offset-less string to `new Date()`, which interprets it in the **phone's** time zone instead. Meanwhile the ETA it's compared against (`closestHour(hourly, stop.eta)`) is a true absolute timestamp built from the phone's clock.

So when a stop is in a different time zone than the phone, every comparison is skewed by the zone difference. Concrete example: planning from Salt Lake City (Mountain time) to Las Vegas (Pacific): for stops in Nevada, a 3pm-Pacific arrival gets matched against the forecast labeled "3pm" *Pacific wall clock* interpreted as *Mountain* — i.e., the 2pm-Pacific forecast. An hour matters for wind (which often builds through the afternoon), and it matters more for the temperature/precip icons around weather fronts. Many great RV corridors cross zone lines (UT→NV, AZ→NM in summer with DST quirks, TX→NM…).

### Fix

Ask Open-Meteo for absolute timestamps instead — add `&timeformat=unixtime` to the hourly URL and parse accordingly:

```js
const url = `${BASE}?latitude=${lat}&longitude=${lon}` +
  `&hourly=...` +
  `&temperature_unit=fahrenheit&wind_speed_unit=mph&forecast_days=3` +
  `&timezone=auto&timeformat=unixtime`;
...
time: new Date(data.hourly.time[i] * 1000),
```

Unix times are timezone-independent, so `closestHour()` becomes correct everywhere with no other changes.

(Separate, cosmetic: the displayed ETA on each stop card uses `toLocaleTimeString()`, i.e. the phone's home zone, not the stop's local zone. That's a defensible choice — "your clock" — just worth knowing it's the behavior.)
